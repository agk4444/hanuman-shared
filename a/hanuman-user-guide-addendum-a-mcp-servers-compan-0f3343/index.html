15. MCP servers

Five MCP servers appear in the agent tool manifest, 59 tools total.

Server Tools Purpose
filesystem-mujxjalj0 14 read/write/edit files, directory tree, glob search, move, media, allowed-directories
playwright-mujxjam66 24 snapshot, click, type, navigate, screenshot, network, console, dialogs, drag, evaluate
sqlite-mujxjam35 11 query, execute, schema describe, list/drop/create table, insert/update/delete, transactions
memory-mujxjals2 9 knowledge-graph entities, relations, observations, read_graph, search_nodes, open_nodes
sequential-thinking-mujxjaln1 1 structured deliberation (sequentialthinking)

Status: registered, reachable, and currently non-functional

Four of the five were called directly. Every call failed with the same server-side error:

WRITE_PATTERNS.test is not a function

Diagnosis

This is a code defect in the MCP server's write-authorization layer, not a permission prompt and not a configuration problem.

.test() is a RegExp method. It is being called on a value that is not a RegExp — most likely WRITE_PATTERNS is defined as an array or a plain object where the guard expects a collection of regexes. Because the guard sits in the shared request path, it fires on read-only calls too, which is why list_allowed_directories (filesystem) and read_graph (memory) fail exactly as hard as a write would.

Fix: coerce every WRITE_PATTERNS entry to RegExp at definition, or gate the call on instanceof RegExp before invoking .test(). One-line change; unblocks 59 tools across filesystem, SQLite, a knowledge graph, and a full browser.

The failure mode worth remembering

A manifest listing is not a working tool. All 59 appear callable in the tool list. None are. MCP therefore presents a silent surface: an agent reaches for a tool, gets the error, and loses a turn. Worse, a shallow read treats "the tool is listed" as "the tool works" — which is exactly the mistake I made, in two directions, one turn after writing §14 about it:

  1. I reported MCP as absent because I found no instrument to observe it, without testing the tools that were plainly listed.
  2. A moment later I reported a repetition loop as if it were "equation analysis" in a message claiming the guide edit had succeeded. It had not. No tool call backed any of it.

The corrective is unglamorous: a capability claim needs a call, and a completion claim needs a version number.

Note on Playwright specifically

MCP Playwright (playwright-mujxjam66, 24 tools) duplicates the built-in browser tools, which now work natively following the earlier Playwright fix. That leaves two paths to one capability with one of them dead. Worth designating a canonical path so an agent doesn't silently pick the broken one and report a browser failure that isn't real.

Not verified

No MCP tool has been verified end-to-end. Everything above is either a manifest listing or a failure result. Deferred until the codespace quota is resolved — MCP behaviour under a live VM has not been observed.

Why this is not a v3

artifact_edit takes the full document as its payload, not a diff. Re-reading guide v2 returned the text truncated by the context window (10,496 characters trimmed), preserving §1–§8 and losing everything after.

Writing a v3 from a partial read would have silently destroyed §9 onward — including §11 (known issues), §12 (not verified), §13 (cheat sheet), and §14 (documented mistakes) — and the edit would have reported ok: true and looked like a success. That is the same class of error as the two in §14, and it is worse, because it would have destroyed a document rather than merely misreported one.

To fold this into the guide as v3, either:

  • paste the full guide text (v2 is retrievable via the share link in a browser), or
  • keep this addendum as a standing companion — it is a complete document, not a fragment.

There is no offset or pagination parameter on artifact_get, so the missing tail cannot be fetched in pieces.
